# Weather Delivery Tracker

Checks the weather for each pending order's delivery city, flags orders as
"Delayed" when the weather is bad, and writes a personalized apology message
for every customer whose order got delayed.

## Overview

The script reads `orders.json`, looks up the current weather for each city
concurrently, and applies one rule: if the weather condition is `Rain`,
`Snow`, or `Extreme`, the order status changes to `Delayed`. Every delayed
order then gets a short, friendly apology message generated by an AI
provider. Results are written to the `output/` folder.

A city that fails to resolve (bad name, API error, timeout, etc.) is logged
and skipped. The rest of the orders keep processing.

## Architecture

```
orders.json ──▶ weather.js (Promise.all, one call per city)
                     │
                     ▼
              orderService.js (apply delay rule)
                     │
              ┌──────┴───────┐
              ▼              ▼
   output/updated-orders.json   ai.js (apology per delayed order)
                                      │
                                      ▼
                          output/apology-messages.json
```

- `weather.js` – talks to OpenWeatherMap, one function per city plus a
  batch function that runs them all concurrently.
- `ai.js` – builds the apology prompt and tries AI providers in order until
  one responds; falls back to a template message if all of them fail.
- `orderService.js` – pure logic that merges weather results into orders
  and drives apology generation for the delayed ones.
- `utils.js` – JSON read/write helpers and a small retry wrapper.
- `logger.js` – consistent timestamped console logging.
- `constants.js` – URLs, file paths, timeouts, and other config in one
  place instead of scattered magic values.
- `index.js` – wires everything together and is the only file that runs
  side effects (reading input, writing output).

## Installation

Requires Node.js 18 or newer. Uses ES modules and `fs/promises`, nothing exotic.

```bash
npm install
```

## Setup

Copy the example env file and fill in your keys:

```bash
cp .env.example .env
```

| Variable              | Required            | Notes                                                                                 |
| --------------------- | ------------------- | ------------------------------------------------------------------------------------- |
| `OPENWEATHER_API_KEY` | Yes                 | Free tier at openweathermap.org                                                       |
| `MODEL`               | Yes                 | Which AI provider to try first: `openrouter`, `groq`, `gemini`, `ollama`, or `claude` |
| `OPENROUTER_API_KEY`  | If using OpenRouter | Free tier available                                                                   |
| `GROQ_API_KEY`        | If using Groq       | Free tier available                                                                   |
| `GEMINI_API_KEY`      | If using Gemini     | Free tier available                                                                   |
| `CLAUDE_API_KEY`      | If using Claude     | Paid                                                                                  |
| `OLLAMA_BASE_URL`     | If using Ollama     | Defaults to `http://localhost:11434`                                                  |

You only need the key for whichever provider you set in `MODEL`. The app
will still try the rest in priority order if your chosen one fails, so
having a couple of free-tier keys configured makes the run more resilient.

## Testing

```bash
npm test
```

Runs the Vitest suite (33 tests across 4 files) against mocked HTTP calls,
so no real API keys or network access are needed. Coverage focuses on the
logic most likely to break silently:

- weather lookups: success, 404 (no retry), timeout (retries then
  succeeds or fails), malformed response, missing API key, concurrency
- order processing: the delay rule, unchanged orders, failed lookups,
  duplicate `order_id`s, all-delayed and none-delayed batches, empty input
- AI provider selection: preferred provider succeeds, falls through to
  the next on failure, falls back to the template message when every
  provider fails, Ollama's no-key path, malformed provider responses
- file I/O: valid/malformed/missing JSON, empty arrays, nested output
  paths, retry/backoff behavior

## Linting & Formatting

```bash
npm run lint
npm run format
```

ESLint catches unused variables, dead code, and (via the `preserve-caught-error`
rule) places where an error was re-wrapped without keeping the original as
`cause`. Prettier handles formatting. Both are configured to leave
`node_modules/` and `output/` alone.

## Expected Output

Console logs show each step as it happens, including which city is being
checked, whether it delayed the order, and a summary at the end:

```
INFO  Processing city: New York (order 1001)
INFO  Weather fetched for New York: Rain
INFO  Order 1001 delayed - Rain in New York
...
DONE  Finished: 4 orders processed, 2 delayed, 1 lookups failed
```

Two files get written to `output/`:

- **updated-orders.json** — the original orders with `status` updated to
  `Delayed` where applicable, plus a `weatherCondition` (or `weatherError`
  for failed lookups) on each order.
- **apology-messages.json** — one message per delayed order.

The versions currently checked in under `output/` were produced by
running the script against illustrative weather conditions (not a live
OpenWeatherMap call) and with no AI provider keys configured, so the
apology messages use the code's own fallback template rather than
real AI-generated text — that's the actual, reproducible behavior of
this codebase when no AI keys are set, not a stand-in for one. Running
`npm start` with real OpenWeatherMap and AI provider keys will overwrite
both files with live results.

## Error Handling

- Missing `OPENWEATHER_API_KEY` stops the script immediately with a clear
  message, since nothing useful can happen without it.
- A city that doesn't exist (like `InvalidCity123`) or any other weather
  API failure is caught per-city, logged, and the order is left as-is.
  It doesn't throw, and it doesn't block the other cities.
- A city that doesn't resolve (404) fails immediately instead of wasting
  retries on something that will never succeed. Genuine transient errors
  (timeouts, network issues, 5xx responses) retry up to twice before being
  treated as a failure.
- If every AI provider fails (missing keys, rate limits, network issues),
  the app falls back to a simple template apology so the pipeline still
  finishes instead of leaving a gap in the output.
- Malformed JSON in `orders.json` or an unexpected shape in an API
  response throws a clear error instead of crashing with a cryptic stack
  trace.

## Switching AI Providers

Change the `MODEL` value in `.env` to one of `openrouter`, `groq`,
`gemini`, `ollama`, or `claude`. No code changes needed: `ai.js` reads
this at runtime and tries that provider first, falling back through the
others (in the priority order below) if it fails:

1. OpenRouter (free tier)
2. Groq (free tier)
3. Gemini (free tier)
4. Ollama (local, no key needed, just a running Ollama instance)
5. Claude

## Troubleshooting

- **"OPENWEATHER_API_KEY is not set"** — copy `.env.example` to `.env`
  and add your key. Free tier keys can take a few minutes to activate
  after signup.
- **All cities failing** — double check the key is active and that
  you're not hitting the free tier's rate limit (60 calls/minute).
- **AI messages all using the fallback template** — check that the key
  for your `MODEL` provider is set and hasn't expired; look at the WARN
  lines in the console for the specific provider error.
- **`output/` files not updating** — the script writes fresh files every
  run and creates the folder if it's missing, so this usually means the
  script exited early. Check the console output for an ERROR line.
- **`npm install` fails with a 404 on a package you don't recognize**
  (e.g. `yocto-queue`) — that's a transitive dev dependency several
  levels deep in ESLint's own dependency tree, not something this
  project depends on directly. A 404 here usually means your npm
  registry mirror hasn't cached that package version, not a problem
  with `package-lock.json`. Try `npm install --registry
https://registry.npmjs.org` to bypass the mirror, or ask whoever
  manages it to refresh the cache. `npm start` itself only needs
  `axios` and `dotenv` and doesn't touch the lint/test toolchain at all.

## Assumptions

- `order_id` is treated as a display field, not a lookup key. Orders and
  their weather results are matched by position in the list, so duplicate
  IDs in the input data won't cause one order's weather to overwrite
  another's.
- Only current weather is checked, not a forecast. The live condition
  per city is what matters here, not predicting a delay in advance.
- The three weather-triggered statuses (`Rain`, `Snow`, `Extreme`) are
  matched against OpenWeatherMap's `weather[0].main` field exactly as
  returned by the API.

## Known Limitations

- The OpenWeatherMap free tier only returns current weather, not a
  forecast, so a city with clear skies right now but rain expected at
  delivery time won't get flagged.
- Tests mock all HTTP calls, so they verify the app's own logic (retry
  rules, delay rules, provider fallback) but not OpenWeatherMap's or any
  AI provider's actual current API contract.

## Future Improvements

- Look up a forecast for the delivery window instead of current weather,
  if the use case calls for predicting delays rather than reacting to
  them.
- Cache weather lookups for a few minutes if this ever runs on a schedule
  against the same cities repeatedly, to stay under the API rate limit.
- Add a CI workflow to run lint + tests on every push, now that both
  exist locally.
